# S12-M2.1 Backend Refactoring: Chatbot Service Isolation

Date: 2026-06-02
Scope: split the S12-M2 chatbot agent out of the main backend into an independently built and deployed Spring Boot service.

## 1) Refactoring objective

The original S12-M2 chatbot implementation lived inside the main backend module under:

- `backend/src/main/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/api/chatbot/`
- `backend/src/main/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/config/ChatbotConfig.java`
- `backend/src/test/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/api/chatbot/`
- `backend/src/test/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/config/ChatbotConfigBindingTest.java`

That coupling made the main backend responsible for both IR/Delta/graph APIs and chatbot runtime wiring. The refactoring separated those responsibilities:

- Main backend remains the IR/Delta/graph backend.
- `chatbot-backend` owns chatbot HTTP routing, chatbot configuration, local LLM runtime adapters, prompt assembly, retrieval, quality checks, DTOs, and chatbot tests.
- Frontend chatbot calls target the dedicated chatbot service instead of assuming chatbot endpoints are served by the main backend.
- Docker Compose runs chatbot as a separate service on the application network.

## 2) New module created

A standalone Spring Boot service was added at:

- `chatbot-backend/pom.xml`
- `chatbot-backend/Dockerfile`
- `chatbot-backend/README.md`
- `chatbot-backend/src/main/java/edu/baylor/ecs/cloudhubs/chatbot/`
- `chatbot-backend/src/main/resources/application.properties`
- `chatbot-backend/src/test/java/edu/baylor/ecs/cloudhubs/chatbot/`

The new Java package root is:

- `edu.baylor.ecs.cloudhubs.chatbot`

The module builds independently as a Spring Boot web application and does not depend on the main backend module.

## 3) Code moved from backend

The chatbot package was moved from the main backend package:

- From `edu.baylor.ecs.cloudhubs.mvp.MVPBackend.api.chatbot`
- To `edu.baylor.ecs.cloudhubs.chatbot`

The moved code includes:

- `ChatbotController`
- `ChatbotConfig`
- `ChatbotQueryService`
- `ChatbotHealthService`
- `ChatbotRuntimeHealthChecker`
- `ChatContextService`
- Runtime adapters for local LLM providers
- Prompt assembly classes
- Retrieval classes
- Quality/confidence classes
- Chatbot DTOs and evidence DTOs
- Chatbot-specific provider/guardrail services

All package declarations and imports were updated to use the new package root. The chatbot service was also checked to ensure it no longer references:

- `MVPBackend`
- `edu.baylor.ecs.cloudhubs.mvp`

## 4) Main backend cleanup

The original chatbot agent code was removed from the main backend:

- Deleted `backend/src/main/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/api/chatbot/**`
- Deleted `backend/src/main/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/config/ChatbotConfig.java`
- Deleted old backend chatbot tests under `backend/src/test/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/api/chatbot/**`
- Deleted old `backend/src/test/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/config/ChatbotConfigBindingTest.java`
- Removed chatbot configuration from `backend/src/main/resources/application.yml`

The backend now compiles as an IR/Delta/graph service without chatbot Spring `@Component`, `@Service`, controller, or configuration wiring.

To keep this separation enforced, a guard test was added:

- `backend/src/test/java/edu/baylor/ecs/cloudhubs/mvp/MVPBackend/BackendChatbotIsolationTest.java`

The guard scans backend main sources and resources for chatbot code, endpoint routing, and runtime wiring.

## 5) Endpoint ownership

The REST API paths were intentionally kept unchanged for the chatbot service:

- `GET /chatbot/health`
- `POST /chatbot/query`
- `POST /chatbot/context/refresh`

Ownership changed as follows:

- Before refactoring: the main backend served `/chatbot/**`.
- After refactoring: only `chatbot-backend` serves `/chatbot/**`.

The endpoint routing now lives at:

- `chatbot-backend/src/main/java/edu/baylor/ecs/cloudhubs/chatbot/ChatbotController.java`

The main backend has no `/chatbot` route ownership.

## 6) Configuration split

The chatbot configuration moved out of the backend and into `chatbot-backend`.

The new service maps environment variables through:

- `chatbot-backend/src/main/resources/application.properties`

Supported local model environment variables:

- `CHATBOT_PROVIDER`
- `CHATBOT_MODEL`
- `CHATBOT_BASE_URL`
- `CHATBOT_TIMEOUT_MS`
- `CHATBOT_MAX_TOKENS`
- `CHATBOT_TEMPERATURE`
- `CHATBOT_CONTEXT_BUDGET_MAX_EVIDENCE_ITEMS`
- `CHATBOT_CONTEXT_BUDGET_MAX_EVIDENCE_CHARS`
- `CHATBOT_STRICT_EVIDENCE_ONLY`

The backend service no longer carries these chatbot runtime variables.

## 7) Docker Compose split

`docker-compose.yaml` was updated so backend and chatbot are separate services.

Backend service:

- Remains the IR/Delta/graph backend.
- Depends only on database services.
- No longer receives `CHATBOT_*` environment variables.
- No longer carries chatbot runtime wiring.

Chatbot service:

- Built from `./chatbot-backend`.
- Uses its own container name, `cloudhub_chatbot`.
- Exposes the chatbot service on `8081:8081`.
- Runs on `app_network`.
- Receives the local model `CHATBOT_*` environment variables.

This makes the deployment topology explicit: frontend talks to backend for pipeline/IR/graph APIs and talks to chatbot for `/chatbot/**`.

## 8) Frontend API wiring

Frontend API wiring was updated so chatbot calls use a dedicated service base URL:

- `frontend/src/utils/axiosSetup.ts`
- `frontend/src/services/api.ts`
- `frontend/dockerfile`

The frontend now supports:

- `REACT_APP_CHATBOT_SERVICE_URL`

The chatbot API wrapper uses that value for:

- `GET /chatbot/health`
- `POST /chatbot/query`
- `POST /chatbot/context/refresh`

This removed the previous hardcoded assumption that chatbot endpoints live on the main backend host.

The pipeline UI remains decoupled from transport details:

- `frontend/src/components/pipeline/PipelinePage.tsx` still uses the chatbot panel.
- `frontend/src/components/chatbot/useChatbotState.ts` still calls the generic API functions from `frontend/src/services/api.ts`.

## 11) Current architecture after refactoring

Runtime responsibilities are now separated:

- `backend/`
  - Owns IR APIs.
  - Owns Delta APIs.
  - Owns graph APIs.
  - Owns persistence for the main backend.
  - Does not own chatbot runtime, config, or `/chatbot/**` routes.

- `chatbot-backend/`
  - Owns chatbot REST endpoints.
  - Owns chatbot DTOs.
  - Owns prompt assembly and retrieval orchestration.
  - Owns local LLM runtime adapters.
  - Owns chatbot health checks and strict-evidence behavior.
  - Can compile and test independently from the main backend.

- `frontend/`
  - Calls main backend for normal pipeline APIs.
  - Calls `REACT_APP_CHATBOT_SERVICE_URL` for chatbot APIs.
  - Keeps chatbot UI usage behind the generic API wrapper.

## 12) Important follow-up constraint

The current split intentionally prevents direct Java dependencies from `chatbot-backend` back to `backend`. If chatbot retrieval needs live IR/graph data from the backend, it should be integrated through one of these boundaries:

- Shared contracts module for DTO-only types.
- HTTP client from chatbot service to backend APIs.
- Event/indexing pipeline that publishes evidence artifacts for chatbot retrieval.

The chatbot service should not reintroduce compile-time dependencies on `backend`.
